# **Developer Instruction: HHA Patient ID Synchronization** 

# **Issue** 

When a patient registers through the **MyHealth Vault+ patient portal** , the portal automatically generates an **HHA Patient ID** . 

Example: 

HHA-LAG-202607-0024 

The patient is subsequently created/synchronized into OpenEMR, but the HHA Patient ID is 

# **not currently being transferred to OpenEMR** . 

We have confirmed that OpenEMR already has the correct demographics field and database column: 

- HHA Patient ID 

- **OpenEMR field label:** 

- **OpenEMR field ID:** HHA_ID 

- **Database table:** patient_data 

- **Database column:** patient_data.HHA_ID 

No new demographics field needs to be created. 

# **Current Finding** 

Current OpenEMR audit: 

- Total patients: **54** 

- Patients with HHA Patient ID: **8** 

- Patients missing HHA Patient ID: **46** 

Recent portal-created patients are successfully reaching OpenEMR, but their records look like: 

pid:      59 

pubpid:   59 

HHA_ID:   NULL 

The desired result is: 

pid:      59 

pubpid:   59 

HHA_ID:   HHA-LAG-202608-XXXX 

Do **not** replace or modify pid or pubpid as part of this work. 

# **Required Development Work** 

# **1. Trace the Patient Registration Integration** 

Please identify the backend workflow responsible for: 

Patient registers in MyHealth Vault+ 

↓ 

Portal creates patient/account 

↓ 

HHA Patient ID is generated 

↓ 

Patient is synchronized to OpenEMR 

↓ 

OpenEMR patient record is created 

Locate the API/service/function responsible for creating or updating the corresponding OpenEMR patient. 

Determine where the HHA Patient ID is available in the portal registration workflow and why it is not currently reaching OpenEMR. 

# **2. Add HHA Patient ID to the OpenEMR Synchronization** 

The **existing HHA Patient ID generated by MyHealth Vault+** must be transferred to OpenEMR. 

Required mapping: 

# **MyHealth Vault+ OpenEMR** 

HHA Patient ID patient_data.HHA_ID 

First Name patient_data.fname Last Name patient_data.lname DOB patient_data.DOB Email patient_data.email Mobile Phone patient_data.phone_cell 

The HHA ID must originate from **MyHealth Vault+** . 

Do **not** independently generate another HHA ID inside OpenEMR. 

# **3. Determine Supported OpenEMR API Method** 

Please first determine whether the existing OpenEMR Patient REST API accepts the custom demographics field HHA_ID. 

If supported, include the HHA ID in the normal patient create/update API operation. 

If the standard OpenEMR API does **not** support custom demographics fields, do not modify OpenEMR core files. 

Instead, document the limitation and implement an upgrade-safe integration mechanism, such as an HHA custom module/API endpoint or other supported extension mechanism, to update: 

patient_data.HHA_ID 

The implementation must survive future OpenEMR upgrades. 

# **4. HHA ID Must Be Immutable** 

Once assigned, an HHA Patient ID must not normally change. 

For example: 

HHA-LAG-202608-0042 

must remain associated with that patient throughout the HHA ecosystem. 

If OpenEMR already contains the same HHA ID: 

Portal:   HHA-LAG-202608-0042 OpenEMR:  HHA-LAG-202608-0042 

no action is necessary. 

If OpenEMR is blank: 

Portal:   HHA-LAG-202608-0042 

OpenEMR:  NULL populate it. 

If OpenEMR contains a **different non-empty HHA ID** : 

Portal:   HHA-LAG-202608-0042 

OpenEMR:  HHA-LAG-202607-0017 

# **DO NOT overwrite it automatically.** 

Log/flag the record for reconciliation. 

# **5. Existing Patient Backfill** 

There are currently **46 OpenEMR patients without an HHA Patient ID** . 

. After fixing new registrations, prepare a **one-time reconciliation/backfill** 

The HHA ID must be retrieved from the existing MyHealth Vault+ patient database. 

Do not generate replacement IDs based on the OpenEMR PID. 

Preferred matching order: 

1. Existing stored OpenEMR PID/UUID relationship in the portal, if available 

2. Portal/OpenEMR integration mapping table, if available 

3. Email + DOB 

4. First Name + Last Name + DOB + Email 

Do not automatically update ambiguous matches. 

For example, we already have duplicate/similar patient records in OpenEMR, so name-only matching is unacceptable. 

Produce a reconciliation report containing: 

OpenEMR PID 

Patient Name 

DOB 

Email 

Portal Patient ID 

HHA Patient ID 

Match Method 

Match Confidence 

Action 

Suggested actions: 

AUTO-MATCH 

MANUAL REVIEW 

NO PORTAL MATCH 

CONFLICT 

ALREADY SYNCHRONIZED 

**Do not execute the production backfill until the reconciliation output has been reviewed.** 

# **6. Uniqueness Protection** 

The HHA Patient ID is intended to become HHA's enterprise/master patient identifier across: 

MyHealth Vault+ 

OpenEMR 

Mobile App 

TeleCare 

MinuteCare 

CareTest 

NeuroFlex 

Partner integrations 

Future HHA clinical systems 

Therefore, two different patients must never receive the same HHA Patient ID. 

Please add application-level validation to prevent duplicate assignment. 

Do **not** add a production database UNIQUE constraint/index until the existing patient population has been reconciled and confirmed clean. 

# **7. Logging** 

The synchronization process should log at minimum: 

timestamp 

portal_patient_id 

HHA_ID 

OpenEMR_pid 

operation 

result 

error 

Do not log passwords, access tokens, OAuth secrets, or unnecessary clinical information. 

Example: 

2026-08-13 

Portal Patient: 842 

HHA ID: HHA-LAG-202608-0042 

OpenEMR PID: 59 

Operation: Patient HHA ID Sync 

Result: SUCCESS

# **Acceptance Criteria** 

This task is complete when: 

- New MyHealth Vault+ registrations continue creating the appropriate OpenEMR patient. 

- The portal-generated HHA Patient ID is automatically transferred to OpenEMR. 

- patient_data.HHA_ID contains the exact same HHA ID shown in MyHealth Vault+. 

- OpenEMR does not generate a competing HHA Patient ID. 

- Existing non-empty conflicting IDs are not silently overwritten. 

- Duplicate HHA IDs are prevented. 

- The solution does not require modification of OpenEMR core files. 

- The implementation is upgrade-safe. 

- Synchronization events/errors are logged. 

- Staging testing is completed successfully. 

- A reconciliation report is produced for the existing 46 patients missing HHA_ID. 

- Existing patients are not backfilled in production until the reconciliation results are reviewed and approved.
